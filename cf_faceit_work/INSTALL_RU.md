# CF FACEIT — установка обновлённой версии

## Сайт

1. Разместите **содержимое `PAGES_UPLOAD/`** в корне сайта. Основная страница — `PAGES_UPLOAD/index.html`; `cf_faceit_work/index.html` и корневой `index.html` — другие, неканонические страницы.
2. Проверьте `PAGES_UPLOAD/js/config.js`: `CF_SUPABASE_URL` и публичный `CF_SUPABASE_ANON_KEY` должны соответствовать вашему проекту Supabase. Публичный anon key рассчитан на браузер; **никогда не помещайте в JS или сайт `service_role` key**.
3. Очистка при первом запуске удаляет старые локальные данные прежней demo-версии (`cfFaceit.accounts.v1`, `matches`, `inbox`, `news`), в том числе локально сохранённые пароли и фиктивные результаты. Сессия авторизации Supabase остаётся отдельной.

## Supabase и миграции

`SQL/49_online_tournaments.sql` — **добавочная миграция**, а не полный baseline для нового проекта. Она рассчитана на базу, уже обновлённую до совместимого набора SQL/01–48: профиль `public.profiles` с `id`, `nickname`, `role`, существующая Auth-схема и роли `authenticated`/`anon`. Перед применением сверьте реальные функции, поля и применённые миграции вашей базы. Сначала проверьте на копии/стейджинге; в рамках этой работы SQL в production не запускался.

Миграция создаёт отдельные `cf_tournaments`/`cf_tournament_players`. Чтение выполняется через аутентифицированный RPC; прямой доступ к таблицам закрыт, а регистрация, лимит мест и административные операции проверяются в транзакциях на сервере. Повторное применение безопасно для этой схемы, но **не означает**, что старые скрипты SQL/01–48 можно прогонять повторно.

Исторические SQL-файлы в рабочей копии не образуют проверенный единый installer: часть скриптов перекрывается, требует определённого порядка или меняет/удаляет данные. Не запускайте `SQL/19_FIX_queue.sql` и `SQL/31_clear_all_matches_once.sql` как обычные миграции: они очищают очередь/матчи. Для нового Supabase-проекта единая проверенная установка ещё не подготовлена.

Для выдачи роли владельца используйте только [supabase-founder-admin-setup.sql](supabase-founder-admin-setup.sql), задав **независимо проверенный Auth UUID**; шаблон намеренно падает, пока UUID не задан. Скрипт не подтверждает почту и не определяет владельца по имени или email. Старые роли `founder`, если они уже существуют, нужно отдельно проверить в Supabase — эта миграция автоматически их не отзывает.

## Проверки

Из корня репозитория:

```bash
node --check cf_faceit_work/PAGES_UPLOAD/js/app.js
node --check cf_faceit_work/PAGES_UPLOAD/js/config.js
python3 -m unittest discover -s cf_faceit_work/tests -v
```

Эти проверки покрывают синтаксис и локальные файлы, но не подтверждают применение SQL, работу PostgREST с вашей схемой, состояние Edge Functions, живую регистрацию/матчмейкинг или production-доступность. OCR-проверка результата и фильтр секретов в поддержке зависят от существующего Edge Function/SQL и требуют отдельной проверки; снимок экрана не доказывает честность счёта.
